# 작업 내역

OpenCAD DWG·DXF(2026-10-16까지 이름은 2D 뷰어, 저장소 `2dcad-viewer`)를 만들어 온 과정을 단계별로 정리했습니다. 커밋 하나하나는 `git log`에, 남은 일은 [ROADMAP.md](ROADMAP.md)에 있습니다.
모든 기능은 브라우저 안에서만 동작하며, 연 파일은 사용자 컴퓨터 밖으로 나가지 않습니다.

## 2026-10-28(13차): AUTOSNAP 마그넷과 극좌표·객체 스냅 추적 비트

AutoCAD 도움말의 AUTOSNAP(레지스트리에 저장, 초기값 63)은 1 표식기, 2 AutoSnap 툴팁, 4 마그넷, 8 극좌표 추적, 16 객체 스냅 추적, 32 추적 툴팁입니다.
12차에 비트 뜻은 바로잡았지만 마그넷(4)은 읽기만 하고 십자선은 늘 커서 자리에 있었습니다. F10·F11은 AUTOSNAP과 따로인 세션 값이라 시작할 때마다 꺼져 있었고,
AUTOSNAP을 바꿔도 추적이 그대로였으며 F10을 눌러도 AUTOSNAP이 그대로였습니다.

### 마그넷
- 도움말은 마그넷을 커서를 가장 가까운 스냅점으로 끌어 고정하는 기능으로 설명합니다(OPTIONS 제도 탭의 마그넷 칸, AutoSnap 설명).
  켜 두면 잡은 객체 스냅점에 십자선이 붙습니다. 툴팁과 동적 입력 칸도 그 자리를 따라갑니다. 끄면 표식기만 스냅점에 보이고 십자선은 커서 자리에 있으며,
  누르면 어느 쪽이든 스냅점을 씁니다.
- 극좌표·객체 스냅 추적의 정렬점에는 붙이지 않습니다. 도움말의 마그넷은 AutoSnap(객체 스냅)에만 있습니다.
- 휴대폰의 정밀 조준 십자선도 마우스 십자선과 같게 스냅점에 붙습니다.

### 극좌표·객체 스냅 추적(F10·F11)
- F10·Ctrl+U·F11, 상태 막대 단추, 제도 설정(DSETTINGS), OPTIONS, 변수 이름 입력, SYSVDLG, SETVAR, AutoLISP `setvar`(AUTOSNAP·POLARMODE)가 모두 AUTOSNAP 8·16 한 값을 읽고 씁니다.
  이 값은 이 브라우저에 남아 다음에 열어도 같은 상태로 시작합니다. 처음에는 63이라 두 추적이 모두 켜져 있습니다(AutoCAD와 같고, 전에는 꺼져 있었습니다).
- 직교와 극좌표 추적은 함께 켤 수 없습니다. 직교를 켜면(F8·ORTHOMODE) 8을 끄고, 어디서든 8을 켜면 직교를 끕니다. 16을 끄면 획득점(+)을 지웁니다.
- AUTOSNAP은 도면에 저장하지 않습니다. DXF·DWG 머리말에 이 변수가 없고 AutoCAD도 레지스트리에 둡니다. 도면을 열어도 추적 상태는 바뀌지 않습니다.
- OPTIONS 제도 탭에 AutoCAD와 같은 AutoTrack 설정의 AutoTrack 툴팁 표시(K)(32) 칸을 더했습니다. 저장할 때는 지금 AUTOSNAP의 추적 비트를 그대로 둡니다.
- SETVAR가 머리말 변수만 찾아 AUTOSNAP·PICKBOX 같은 이 브라우저 변수나 POLARMODE·DYNMODE 같은 세션 변수를 주면 "이 도면에 없습니다"로 끝나던 것을,
  변수 이름을 바로 친 것과 같은 프롬프트로 받게 고쳤습니다.
- 끝점을 객체 스냅 추적과 연장선이 함께 얻으면 획득점 +를 하나만 그립니다.

### 남긴 것
- POLARMODE는 이 앱에서 극좌표 추적 켜기·끄기(AUTOSNAP 8과 같은 상태)로 남겼습니다. AutoCAD의 POLARMODE는 각도 측정·추적 방식 비트라 뜻이 다릅니다(ROADMAP).
- 지연된 접점을 첫 점으로 찍었을 때 극좌표 추적은 찍은 자리를 기준점으로 씁니다. 도움말에 이 경우가 없어 바꾸지 않았습니다.
- 스플라인 조정점·맞춤점과 다중 지시선 정점의 평탄 좌표는 이번에 하지 않고 크기만 쟀습니다(Node 힙, 5만 개씩).
  조정점 8개를 점 객체 배열로 두면 760B, 수 배열로 두면 248B라 스플라인 하나에 약 500B를 줄일 수 있습니다.
  다중 지시선은 선 하나의 정점이 평균 1개라(실제 도면 2,507개에 2,600개) 선 객체 184B가 120B로 줄 뿐이어서 뒤로 미뤘습니다.

### 확인
- 시험: 로컬 대조 없이(CI 조건) 270개 파일·2,982개 통과(12차 2,975개에 새 시험 7개, 대조 13개 파일 건너뜀).
  `npm run test:oracle` 283개 파일 4,016개 통과. 실패 2개는 기계 부하(부하 평균 70~90) 탓인 비교 시간 시험과 끌어 옮기기 시험의 모듈 불러오기 대기이고,
  따로 돌리면 통과합니다. typecheck와 빌드도 통과합니다.
- 헤드리스 Chrome(새 임시 프로필): 넓은 화면·밝은 테마에서 처음 63(두 추적 켜짐), F10 → 55, F11 → 39, 상태 막대 단추 → 47, F8 → 직교 켜짐·극좌표 꺼짐(39),
  AUTOSNAP 63 → 직교 꺼짐, SETVAR AUTOSNAP 47, DSETTINGS 칸과 OPTIONS 칸이 같은 값, OPTIONS에서 마그넷만 끄고 저장해도 F10·F11 단추 그대로,
  마그넷을 끄면 십자선이 커서 자리·켜면 끝점에 붙음, 새로 고침 뒤에도 같은 상태. 375px·어두운 테마에서 F10과 상태 막대 단추, OPTIONS 제도 탭(가로 넘침 없음). 콘솔 오류 없음.
- 실제 도면 2,770개 훑기(ezdxf 대조 포함)가 12차 결과와 같습니다(분류·지표가 바뀐 파일 0, 새 예외 0). 파일 해석은 바꾸지 않았습니다.

## 2026-10-28(12차): 로컬 대조 전체 시험의 스플라인 실패 바로잡기, AUTOSNAP 비트

로컬 대조 자료(ezdxf, DWG 기준 도구, 표본 폴더)를 모두 주고 전체 시험을 돌리면 스플라인 시험 15개가 실패했습니다
(같은 핸들 객체 비교 2개, DWG 리더 대조 2개, DWG 쓰기 대조 11개). 10차 병합 전에는 통과했고, CI는 대조 시험을 건너뛰어 드러나지 않았습니다.

### 무엇이 달랐나
- 실패는 모두 같은 종류입니다. DWG의 맞춤점 자료를 읽은 스플라인에 DWG 리더가 조정점·매듭을 채웠는데, 기준 쪽에는 조정점·매듭이 0개입니다.
  표본(sample_AC1027·AC1032)의 SPLINE 434는 DWG에 맞춤점 2개와 끝 접선만 있습니다. 같은 도면을 AutoCAD가 쓴 DXF에는 조정점 4개·매듭 8개가 있고,
  DWG 리더가 채운 값과 좌표·매듭까지 같습니다. 기준 DXF는 AutoCAD가 쓰지 않은 DXF라 맞춤점만 적습니다(70의 매듭 매개변수 비트도 잃습니다).
  DWG 쓰기 대조 11개도 우리가 쓴 맞춤점 자료를 기준 도구가 맞춤점만으로 DXF에 적은 것입니다(맞춤점 수는 같습니다).
- 따라서 읽기·쓰기가 틀린 것이 아니라 기준 쪽 표현 차이입니다. 코드는 고치지 않았습니다.

### 바뀐 것(시험만)
- 대조 비교에서 맞춤점만 적힌 기준을 AutoCAD DXF 꼴로 바꿔 견줍니다(`tests/dwg/normalize.ts` 11번). 요약 비교는 조정점 = 맞춤점 + 2, 매듭 = 맞춤점 + 6이고,
  훑기 ezdxf 대조와 같은 도우미(`tests/oracle/spline.ts`)를 씁니다. 같은 핸들 객체 비교는 그 맞춤점 자료로 AutoCAD 방식 조정점·매듭을 구해 좌표까지 견줍니다.
  맞춤점 수·좌표·끝 접선·차수는 그대로 견주고, 우리 쪽 수가 AutoCAD 규칙과 다르면 지금처럼 차이로 남습니다.
- DWG 리더가 채운 조정점·매듭·70이 같은 도면을 AutoCAD가 쓴 DXF와 같은지 보는 로컬 대조 시험을 더했습니다(위 판단의 근거를 지킵니다).
  DWG 리더가 매듭 매개변수를 잘못 쓰게 일부러 바꾸면 이 시험과 같은 핸들 비교가 함께 실패하는 것도 확인했습니다.
- 대조 캐시를 여러 워커가 함께 만들 때 쓰는 중인 빈 DXF를 읽어 "빈 파일입니다"로 실패하던 것을, 임시 이름에 다 쓴 뒤 옮기게 고쳤습니다(기준 DXF·ezdxf 요약).
- `npm run test:oracle`: 세 변수를 모두 쓸 수 있을 때만 전체 시험을 돌리고, 하나라도 없으면 무엇이 없는지 알리고 멈춥니다. README 개발 절에 큰 변경 전후로 돌리라고 적었습니다.

### AUTOSNAP 비트
- AutoCAD 도움말의 AUTOSNAP은 1 표식기, 2 AutoSnap 툴팁, 4 마그넷, 8 극좌표 추적, 16 객체 스냅 추적, 32 추적·직교 툴팁입니다(초기값 63).
  이 앱은 2를 마그넷, 4를 툴팁으로 읽어, AutoCAD처럼 `AUTOSNAP 61`(툴팁 끄기)을 주면 툴팁이 그대로 보이고 `59`(마그넷 끄기)를 주면 툴팁이 꺼졌습니다.
  스냅 이름 툴팁과 OPTIONS 제도 탭의 표식기·마그넷·툴팁 칸을 도움말의 비트로 읽고 씁니다. 전에 OPTIONS에서 마그넷이나 툴팁 칸 하나만 끈 브라우저는
  그 값이 다른 칸으로 읽힙니다(기본값 63은 그대로). 마그넷과 추적 비트의 동작은 아직 없습니다.

### 확인
- 고치기 전: 로컬 대조를 준 전체 시험 283개 파일 중 4개 파일·16개 실패(스플라인 15개, 기계 부하 탓인 비교 시간 시험 1개).
  고친 뒤: `npm run test:oracle` 283개 파일·4,011개 통과(2개 건너뜀 — 부하가 높을 때 비교 시간 시험이 2초를 넘기면 따로 돌려 통과를 확인했습니다).
  로컬 대조 없이(CI 조건) 270개 파일·2,975개 통과(대조 13개 파일 건너뜀). typecheck와 빌드도 통과합니다.
- 실제 도면 2,770개 훑기(ezdxf 대조 포함)가 11차 결과와 같습니다(분류·지표가 바뀐 파일 0, 새 예외 0, ezdxf 대조 요약도 같음).

## 2026-10-28(11차): 큰 도면의 남은 정점 평탄 좌표

2026-10-16에 경량 폴리선·해치 폴리선 경계에 한 것처럼, 남은 정점 객체를 수 배열로 바꿔 큰 도면의 문서 메모리와 GC를 줄였습니다.
저장 결과(DXF·DWG)와 장면 그림의 지문은 고치기 전과 같습니다(정점 섞음 100만 객체 DXF `4fefaee731417f7f`·DWG `d786f2e92805e53b`·장면 `f6ada541bc7a1569`,
기본 섞음 100만 객체 DXF `66a2d13a0eb5fbd0`·DWG `bc5d69323b08d885`·장면 `3a8c2639c3df4edb`).

### 무엇부터 했나
실제 도면 2,770개 가운데 이 객체가 든 1,004개를 읽어 정점·점 객체 수를 셌습니다.
POLYLINE 25,428개(정점 52,952개: 2D 24,462·3D 27,438·폴리페이스 1,031·메시 21), 해치 모서리 경로 4,781개(모서리 23,964개: 선 21,583·호 2,350·타원호 21·스플라인 10),
MESH 80개(정점 5,040·면 5,440·모서리 10,400), 스플라인 856개(조정점 6,801·맞춤점 309), 지시선 622개(정점 2,097), 다중 지시선 2,507개(정점 2,600)입니다.
객체가 많은 차례로 POLYLINE, 해치 모서리, MESH, 지시선을 바꿨습니다.

### 정점 평탄 좌표
- POLYLINE(2D·3D·다각형 메시·폴리페이스): 정점마다 객체와 위치 객체를 두지 않고 `verts` [x, y, z, …]에 둡니다. 볼록·정점별 폭·VERTEX 플래그·곡선 맞춤 접선·폴리페이스 면 번호는
  값이 있을 때만 배열(`bulges`·`widths`·`vflags`·`tangents`·`faceRecs`)로 둡니다. 도우미는 `src/core/polyverts.ts`입니다.
- 해치·MPOLYGON 모서리 경계: 모서리 객체 대신 종류 번호로 시작하는 기록을 이은 수 배열 `edgeData` 하나로 둡니다(선·호·타원호·스플라인, 없는 값도 그대로). 도우미는 `src/core/hatchedges.ts`입니다.
- MESH: 정점 `verts`, 면 `faceData` [정점 수, 번호…], 모서리 `edgePairs` [a, b, …]로 둡니다(`src/core/meshdata.ts`).
- 지시선(LEADER): 정점을 `verts` [x, y, z, …]로 둡니다(`src/core/flat3.ts`).
- DXF·DWG 읽기는 정점 객체를 만들지 않고 배열에 바로 담고, 쓰기·장면 빌더는 배열을 바로 읽습니다. 편집 계산(그립·PEDIT·STRETCH·변환·반전·분해·구속·해치 경계·AutoLISP 정점 entget/entmod 등)은
  풀어 쓴 정점으로 계산한 뒤 되담습니다. 구조화 복제가 수를 상자에 담으므로 객체 복제와 워커가 받는 편집에서 POLYLINE 평탄 좌표도 다시 담습니다.
- 객체 하나의 메모리(Node 힙, 한 종류만 5만 개 읽은 뒤 차이): 2D 폴리선(정점 4.5개) 1,207 → 506B, 볼록·폭 2D 폴리선(정점 6.5개) 1,856 → 739B, 3D 폴리선(정점 5개) 1,516 → 609B,
  폴리페이스(정점 8·면 6) 4,139 → 1,681B, 다각형 메시(정점 9개) 2,376 → 746B, 선·호 모서리 해치 1,972 → 1,109B, 지시선 743 → 393B.
  실제 도면 평균 크기의 MESH(정점 63·면 68·모서리 130)는 15,930 → 6,666B입니다.

### 잰 값
`scripts/perf/gen-big.ts`에 정점이 많은 객체를 섞는 `--mix verts`(볼록·폭 2D 폴리선, 3D 폴리선, 폴리페이스·메시, 선·호 모서리 해치, 스플라인, 지시선)와 한 종류만 만드는 `--only`를 더했습니다(기본 섞음 파일은 예전과 같습니다).
정점 섞음 100만 객체(460MB DXF)를 `scripts/perf/measure.ts`로 고치기 전·후 두 번씩 쟀습니다. 기계 부하가 40~190으로 높아 시간·최대 메모리는 흔들립니다.

| 장면 뒤 힙 | 1,123MB | 851MB |
| 장면 만들기 중 GC | 4.2~7.0초 | 2.5~4.0초 |

  - 스플라인은 곡선 매개변수 위에서 접선 조건의 부호가 바뀌는 구간을 가두고 뉴턴법(구간을 벗어나면 이분법)으로 다듬은 뒤, 잔차가 큰 근(곡선 위의 점 자신, 꺾인 매듭)은 버립니다.

## 2026-10-27: 실제 도면 훑기로 찾은 왕복 차이 고치기

실제 도면 2,770개를 읽기 → 장면 → DXF·DWG 쓰기 → 다시 읽기로 훑은 결과(`npm run sweep`)에 남은 왕복 차이를 원인부터 보고 고쳤습니다.
옳은 값은 같은 도면을 AutoCAD가 DWG와 DXF로 쓴 짝(663쌍)과 ezdxf 대조로 정했습니다. 고친 뒤 같은 표본으로 다시 훑어 왕복 차이가 있는 파일이 518개에서 407개로 줄었고,
새 예외나 새로 생긴 차이는 없습니다.

### 자료가 바뀌던 것
- DXF로 연 도면의 여러 줄 문자·공차 줄바꿈이 DWG로 저장하면 `^J` 글자로 들어가던 문제. DXF 파일은 제어 문자를 `^J`·`^I`, 글자 ^를 `^ `로 적는데(AutoCAD와 같다)
  리더가 이 표기를 풀지 않았습니다. 이제 읽을 때 풀고 쓸 때 다시 적어 DXF와 DWG에서 같은 문자가 됩니다(DWG를 DXF로 썼다 읽으면 문자가 달라지던 49개 → 0개).
  여러 줄 문자 편집기가 탭을 `^I`로, 글자 ^를 `^ `로 넣던 것과 ACIS 자료의 `^ `를 따로 다루던 것도 함께 고쳤습니다.
- DWG로 저장하면 스플라인 플래그가 바뀌던 문제(0 → 1160, 닫힘 1 → 521 등). DWG R2013+의 스플라인 값과 DXF 70의 짝을 AutoCAD 실물로 다시 정했습니다:
  첫 값이 1인 맞춤점 스플라인만 1024와 매듭 매개변수(32 현 길이·64 제곱근·128 균일)가 붙고, 닫힘은 1입니다. 맞춤점만 있는 스플라인을 균일 매듭으로 써서
  AutoCAD에서 모양이 달라질 수 있던 것도 고쳤습니다(DXF 70에 비트가 없으면 AutoCAD 기본인 현 길이).
- DXF로 저장하면 2D 폴리선 정점의 Z를 고도로 덮어 쓰고, DWG에서 읽으면 0인 정점 Z를 고도로 바꾸던 것. AutoCAD처럼 정점 Z를 그대로 둡니다(그릴 때는 고도를 씁니다, 88개 → 0개).

### 여러 단 문자
- R2000~R2013 형식(DXF·DWG)으로 저장된 여러 단 문자는 단마다 MTEXT가 따로 있고 첫 단의 확장 자료가 단을 잇습니다. 한 단을 눌러도(창·올가미·명령의 객체 선택도)
  모든 단을 함께 골라 옮기기·지우기·특성 바꾸기가 묶음 전체에 됩니다. 저장하면 단 객체와 확장 자료가 그대로 남고, 복사본은 원본 단을 가리키지 않는 보통 여러 줄 문자가 됩니다.

### 훑기 도구
- 비그래픽 객체(재질·비주얼 스타일·단면 뷰 스타일 등)가 빠지는 것은 설계대로임을 확인했습니다. 해석하지 않은 객체는 같은 형식·판으로 저장할 때만 원본 자료로 남고,
  다른 형식·판으로는 옮길 자료가 없어 저장 전 확인에 알리고 뺍니다(AutoCAD는 기본 재질·비주얼 스타일을 열 때 다시 만듭니다). 훑기는 이것을 `objectsDropped`로 따로 세고,
  알리지 않고 빠진 객체만 왕복 차이와 품질 지표(`silent-object-loss`)로 남깁니다. DWG에 자리가 없는 스플라인 평면·직선 비트는 견주지 않습니다.

## 2026-10-16 (4): 저장소 이름 opencad-dwgdxf와 AutoCAD처럼 편집하기

다른 OpenCAD 저장소(opencad-nc·step·skp)처럼 저장소 이름을 `opencad-dwgdxf`로 바꾸고, 대표 주소를 `https://gyutae-kim.github.io/opencad-dwgdxf/`로 옮겼습니다.

### 이름과 시작 화면
- 제목·검색 설명·시작 화면·정보 창·창 제목·공유 이미지를 "그리고·고치고·저장하는 DWG·DXF 2D 캐드"로 바꿨습니다.
- 시작 화면에 새 도면(mm·인치) 단추를 두었습니다(`NEW metric`·`NEW imperial`은 대화상자 없이 만듭니다).

### 직접 조작
- 선택한 객체를 그립이 아닌 곳에서 끌면 이동, Ctrl을 누른 채 놓으면 복사합니다. 빈 곳에서 끌면 올가미(스페이스로 걸침·윈도우·울타리)이고, 걸릴 객체를 미리 강조합니다.
- 오른쪽 클릭은 옵션 없는 프롬프트에서 Enter, 그 밖에서는 상황별 메뉴입니다(SHORTCUTMENU·시간에 민감한 오른쪽 클릭). 브라우저 메뉴는 입력란 밖에서 막습니다.
- 동적 입력이 켜져 있으면 두 번째 점부터 친 좌표는 상대 좌표(`#`은 절대)이고, 커서 옆 거리·각도 칸을 Tab으로 옮기며 잠급니다. 스크립트·AutoLISP 입력은 늘 절대 좌표입니다.
- 점 프롬프트에서 END·MID·CEN·TAN 같은 스냅 이름, FROM·M2P·TT·점 필터를 칠 수 있고, 접점·연장선·평행·가상 교차점·기하학적 중심 스냅을 더했습니다. 기본 객체 스냅은 AutoCAD 기본(OSMODE 4133)입니다.
- 두 번 누르면 문자는 제자리 편집기, 선·원·호는 빠른 특성, 폴리선은 PEDIT, 블록은 블록 편집기입니다. 객체를 고른 직후 같은 자리를 다시 눌러도 그립 편집 대신 두 번 누르기로 봅니다.
- 다기능 그립: 그립 위에 커서를 0.5초 두거나 오른쪽 클릭하면 정점 추가·제거, 호/선 변환, 길이 조정, 반지름, 치수 문자 위치, 연속·기준선 치수. 그립 편집은 모드 전환·Ctrl 다중 복사·여러 핫 그립·동적 치수(입력값 = 결과 길이)를 합니다.

### 명령
- 그리기·수정 옵션: RECTANG·CIRCLE Ttr·PLINE 호·XLINE·ELLIPSE 호·SPLINE, 명령행 ARRAYRECT·ARRAYPOLAR(예전 대화상자는 ARRAYCLASSIC), UNDO 옵션, LENGTHEN 동적, PEDIT 정점 편집, TRIM·EXTEND 걸치기·울타리·Shift 전환, MOCORO, REVCLOUD 수정, 3DPOLY·3DFACE·TRACE, CHAMFER 각도 방식 폴리선 수정.

## 2026-10-16 (2): 큰 도면 정점 평탄 좌표·워커 문서 부호화

큰 도면의 문서 메모리와 GC, 워커가 문서를 보내는 시간을 줄였습니다. 합성 100만·300만 객체 DXF로 쟀고, 저장 결과(DXF·DWG)와 장면 그림의 지문은 고치기 전과 같습니다(100만 DXF `66a2d13a0eb5fbd0`·DWG `bc5d69323b08d885`·장면 `db866df2c5f7dc92`, 300만 DXF `231005554c3d04af`·장면 `5ffd8919102f920a`).

### 정점 평탄 좌표
- 경량 폴리선(LWPOLYLINE) 정점을 정점마다 객체로 두지 않고 수 배열 `verts` [x, y, 볼록, …]와 `widths` [시작 폭, 끝 폭, …](모두 0이면 없음)로 둡니다. 해치 폴리선 경계도 `verts` 하나로 둡니다.
- 읽기·쓰기·장면 빌더는 배열을 바로 읽고, 편집 계산은 `src/core/lwpoly.ts`의 도우미로 정점을 풀어 쓴 뒤 되담습니다.
- Float64Array 대신 보통 수 배열을 썼습니다. 객체마다 형식 배열을 두면 ArrayBuffer 몫으로 폴리선 하나에 150B 넘게 더 들고 화면 스레드에서 되살리기도 느렸습니다. 구조화 복제는 수 배열의 수를 하나씩 상자에 담으므로 객체 복제(cloneEntity)와 워커가 받는 편집에서 평탄 좌표를 다시 담습니다.
- 100만 객체: 읽은 뒤 문서 힙 670MB → 555MB(경량 폴리선 하나 717B → 605B, 해치 1,409B → 1,049B), 읽기 최대 메모리 1,314MB → 1,029~1,175MB, 장면 만들기 중 GC 1.85초 → 0.94~1.40초(기계 부하 4~60에서 잼, 시간 값은 부하에 따라 흔들림). 300만 객체: 읽은 뒤 문서 힙 1,848MB → 1,504MB, 최대 메모리 5,917MB → 4,695MB.

### 워커 문서 부호화
- 속성 모양마다 속성을 이름으로 바로 읽는 쓰기 함수를 만들어 씁니다(속성 읽기가 한 모양만 보고, 수 값을 상자에 담지 않습니다). 수만 든 배열(평탄 좌표·매듭 등)은 값마다 태그를 쓰지 않고 이어 적고, 화면 스레드는 꼭 맞는 크기의 실수 배열로 되살립니다.
- 100만 객체 모형 공간 부호화(묶음을 넘겨 버리는 실제 조건, 같은 부하에서 번갈아 잼): 0.90~1.01초 → 0.68초, 장면 전에 처음 만질 때 1.23~1.48초 → 0.85~0.99초.
- 화면 스레드가 문서를 받는 CPU는 1.85초 → 1.03초, 메시지 하나에 멈추는 가장 긴 시간은 371ms → 65ms가 됐습니다(300만 객체 541ms → 157ms).

### 남은 일
- 2D·3D POLYLINE 정점(객체 하나 1,266B), 스플라인 제어점·맞춤점, 해치 모서리(선·호) 경계, 지시선·메시 정점은 아직 객체 배열입니다. 남은 문서 메모리의 대부분은 객체 자체의 공통 속성과 점 객체(선 하나 360B)입니다.

## 2026-10-16: 3D 뷰어 — NC·STEP·SKP

로드맵의 "다른 형식"을 같은 저장소에서 시작했습니다. NC·MPR·Heidenhain·STEP·SKP 파일을 열면 2D 도면과 같은 파일 탭에 3D 문서로 열립니다.
모두 서버 없이 브라우저 안(웹 워커)에서 읽습니다. 다른 3D 엔진이나 형식 라이브러리를 쓰지 않고 공개 명세·공개 자료 파일만 보고 새로 작성했습니다.

### 3D 뷰어
- WebGL2로 직접 만든 뷰어: 왼쪽 끌기 회전, 가운데·오른쪽 끌기 이동, 휠 확대, 뷰 큐브와 표준 뷰(위·앞·오른쪽·등각), 원근·평행, 음영·윤곽·와이어프레임·X-ray, 측정, 그림 저장.
- 실제 GPU에서 선분 300만 개·삼각형 100만 개를 끌어도 끊기지 않습니다.

### NC
- G-code(ISO·Fanuc·LinuxCNC·GRBL·Mach3 방언 자동 판별): 직선·호·나선, 평면·단위·좌표계, 고정 사이클, 부프로그램, 변수와 IF/WHILE.
- Heidenhain 평문(.h)과 woodWOP MPR(공작물, 수직·수평 드릴, 윤곽 가공, 홈, 포켓, 꺼진 가공).
- 패널: 코드 보기(경로를 고르면 그 줄로, 줄을 누르면 그 경로 강조), 공구 목록·켜고 끄기, 통계·예상 시간, 재생(공구 위치 표시, ×1·×10·×100).
- 100만 줄(32MB) G-code를 약 0.5초에 읽습니다.

### STEP
- AP203·AP214·AP242의 B-rep(평면·원기둥·원뿔·구·원환·B-스플라인·회전·밀기 곡면)을 틈 없이 삼각화하고, 조립·색·단위를 읽어 제품 나무로 보입니다.
- 공개 STEP 21개를 실패 면 없이 읽었고, NIST 시험 모형 9개는 모두 틈이 없습니다.

### SKP
- SketchUp 2021~2026 파일의 면(구멍 포함)·모서리·재질 색·그룹/컴포넌트·태그를 읽습니다. 공개 표본 파일의 바이트만 보고 분석했습니다(docs/formats/skp.md).
- 2020 이하 파일은 형식이 완전히 달라 아직 읽지 못하고 안내합니다.

### 이 단계의 한계
- NC의 회전축(4·5축)·선반 코드, 반경 보정 경로, STEP 와이어프레임·PMI, SKP 무늬는 아직 그리지 않습니다.
- 실제 휴대폰 기기와 큰 실물 파일로 더 확인해야 합니다.

- 채우기(FILL), 빠른 문자(QTEXT), 끌기 모드(DRAGMODE): 화면·PDF·SVG·플롯이 같은 규칙으로 그립니다.

### 파일 형식
